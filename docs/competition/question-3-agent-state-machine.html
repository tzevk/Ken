Question 3 — states

Vantage's runtime state machine

A full audit before an answer: the generic model attacked and discarded, a two-machine design tested on its merits, seventeen distinct unhappy paths given seventeen distinct recoveries, then red-teamed and checked for originality before being written up for judges.

H1–H9Preserved design decisions

Carried forward unchanged from Questions 1 and 2. Everything below is built to hold these, not to reinterpret them.

H1

Deterministic financial truth. The LLM never performs authoritative arithmetic.

H2

Agentic reasoning belongs at the decision moment, not primarily in chat.

H3

Consequence, not judgment. Vantage says what changes, never good/bad.

H4

Silence is a valid action. Not maximizing interventions is a legitimate outcome.

H5

Declining dependency: fewer unnecessary interventions over time, without worse alignment.

H6

Accountable for understanding a consequence before commitment — not for the user's choice.

H7

Conservative L3: bounded autonomy over the attention process, not financial authority.

H8

Execution boundary: money movement, debt, goal changes always need explicit human authority.

H9

Dynamic autonomy governor: At = f(P, Ct, Rt, Dt). Permission is a ceiling, never an instruction to act.

Part 1Attacking the generic state machine

The default shape most teams reach for:

USER INPUT → FETCH DATA → ANALYZE → RECOMMEND → USER APPROVES → ACTION → SUCCESS / FAILURE

Discarded outright, not improved. Six specific reasons it cannot represent Vantage:

  1. No terminal state for correct silence. Every cycle funnels toward a recommendation — H4 has nowhere to live. "Nothing happened" isn't a state here; it's an absence, which makes it unauditable later.
  2. "ANALYZE" collapses the one boundary the product exists to preserve. H1 separates deterministic arithmetic from agentic judgment. One box hides that line from a financial-risk reviewer entirely.
  3. "RECOMMEND → APPROVES → ACTION" is the L2 shape, not conservative L3 (H7). Most events should never generate a proposal at all.
  4. No representation of evidence quality. ANALYZE assumes data is always sufficient — directly contradicting H9's premise that missing data must never silently produce false confidence.
  5. SUCCESS/FAILURE is too coarse for H3/H6. A user proceeding after ASK can be a success. This shape has no room for that, nor for ABSTAIN as a third outcome.
  6. It's linear and single-machine. It can't express the same lifecycle stage behaving differently under different evidence conditions — the actual content of H9.

Part 2What counts as a state

A state is a condition where entering it changes at least one of: what Vantage is waiting for, what it's permitted to do, what it believes it knows, what human authority is required, what transition can happen next, or what must be recorded.

Explicitly not states: a tool call (implementation detail inside a state), a single deterministic calculation (unless its output changes one of the six), a UI screen (presentation, not runtime condition), a raw API response (only the validated result can trigger a transition), an action (the output of entering a state, not the state itself).

This is why "memory updated" — offered as a hypothesis — is not modeled as a visited state below: nothing ever waits there. It's an atomic write performed while transitioning into CLOSED.

Part 3Two interconnected machines

Two machines, not one — and not independent. Machine B gates Machine A's transition guards.

Machine A — Financial Decision Lifecycle

Per-event, ephemeral. OBSERVED → CONTEXT_ASSEMBLED → CONSEQUENCE_COMPUTED → RELEVANCE_ASSESSED → { SILENT | INFORMED | AWAITING_HUMAN_DECISION | ESCALATED | ABSTAINED } → CLOSED, with PENDING_EVIDENCE as a recoverable hold, POST_HOC as the late-arrival branch, and CORRECTED as a post-closure amendment.

The prompt's "user decision" and "outcome observed" are merged into AWAITING_HUMAN_DECISION's resolution — at this design stage, Vantage has no execution power, so the human's response is the outcome; there's no daylight to model separately.

Machine B — Autonomy Governor

Not an independently-persisted, transitioning machine. A deliberate answer to the prompt's open question: P (the standing mandate) is real persisted state, changed only by explicit user action. Ct, Rt, Dt are computed fresh at each checkpoint from currently-observable facts — there's no history to recover, because they aren't stored, they're recalculated.

Machine B's output — what Machine A's guards actually read — is one of four operating envelopes:

EnvelopeMeaning
FULL_ENVELOPECeiling P fully usable
CONTRACTED_ENVELOPEGovernor voluntarily restricts below P — forces INFORM over SILENT, or ASK over autonomous handling
ABSTAIN_REQUIREDEvidence too poor to exercise any of P safely
MANDATE_EXCEEDEDThe needed action sits outside P entirely, regardless of evidence quality

This directly implements H9: P alone never causes an action; the governor decides how much of P is currently earned. Concretely:

CONSEQUENCE_COMPUTED + FULL_ENVELOPE → autonomous classification proceeds CONSEQUENCE_COMPUTED + CONTRACTED_ENVELOPE → ceiling for this event drops one tier CONSEQUENCE_COMPUTED + ABSTAIN_REQUIRED → routes to ABSTAINED, no classification attempted CONSEQUENCE_COMPUTED + MANDATE_EXCEEDED → routes to a human, regardless of confidence

Part 4Happy flow — three legitimate successes

A · Correct silence

Entry OBSERVED, deduplicated by transaction id. Evidence: budget position, buffer, at-risk goals, intervention history — all complete, fresh, corroborated. Calculation: no goal delta crosses the material threshold; buffer floor holds with margin. Reasoning: governor = FULL_ENVELOPE, not material. Trigger → SILENT. Logged: an Intervention record with the trigger facts and the evidence snapshot — an auditable non-event, not a missed one. Why no interaction: H4 — declining to interrupt is the success here. Later verification: if a subsequent goal divergence traces back to this transaction unflagged, it's revisited through the correction protocol (Part 5, U12).

B · Useful information, no friction

Same through CONSEQUENCE_COMPUTED; delta is material but not critical. Governor = FULL_ENVELOPE → autonomous INFORMED. What differs from silence: a consequence statement is generated and shown — a date shift, not a verdict — with nothing to approve. No acknowledgment required, by design (H4's no-friction principle). Closes on delivery, not on being read. Logged with actionTaken: "inform", no userResponse field — INFORM has none.

C · Human decision at the boundary

Same through CONSEQUENCE_COMPUTED; this time a deterministic protected-floor or committed-obligation guardrail fires independent of the softer classifier. Governor forces AWAITING_HUMAN_DECISION regardless of how good the evidence otherwise is. Vantage may show the computed consequence and which stated priority is at risk — it may not call the purchase good or bad (H3), and it may not withhold the transaction itself (H8). Options: continue or reconsider. Continue → CLOSED, userResponse: "continued" — recorded as success if disclosure was accurate and timely, exactly as H6 requires. This single instance never writes to a standing preference on its own; only an explicit, separate user action does that (U10).

Part 6Abstain, as a first-class outcome

Confirmed necessary (U1, U7, U13 all route here). Not one state — a reason code attached to either SILENT or a visible ABSTAINED state, gated by downside, reusing the same governor logic rather than inventing new machinery:

  • Silent-logged abstention (low Dt) — outwardly identical to SILENT, but the record carries reason: insufficient_evidence instead of reason: not_material. A cluster of these on one category is a data-pipeline signal, cleanly distinguishable from "nothing interesting happened."
  • ABSTAINED_WITH_REASON (mid/high Dt) — Vantage states plainly it cannot answer, and why: "I can't tell you what this does to your fund goal — your linked account hasn't synced in 6 days" — rather than a number it can't stand behind.

Stays open if the missing fact is plausibly refreshable before the window closes; closes permanently otherwise. Neither success nor failure: a successful safety behavior under H1/H9, but not an H6 accountability success, since no consequence was actually delivered. Tracked as its own KPI — abstention rate — not folded into either count. Repeated abstention from one source downgrades that source's future reliability weighting (Part 7) and, past a threshold, raises a capability-health flag distinct from any single transaction.

Part 7Making confidence operational — no invented score

No numeric "AI confidence." A deterministic rule table over five observable, per-fact factors:

FactorValues
source_verifiedbool — linked/verified vs. self-reported
freshness_hourstime since refresh vs. a per-fact-type threshold
completenesscomplete / partial / absent
cross_source_agreementagree / disagree / single_source — reuses the existing reconciliation-delta pattern already in the codebase
rail_availabilityavailable / degraded / unavailable — capability-dependent actions only

Precedence — an ordered, short-circuiting cascade, not a weighted blend (fixed after the engineer red-team in Part 14): (1) mandate check, always first and independent; (2) required-fact-absent; (3) staleness; (4) disagreement; (5) protected-boundary/magnitude. First match wins.

Reversibility: whether the decision window is still open — reusing the Q2 finding that a pre-auth cancel is "reversible for the rail, irreversible for the moment." Downside: a composite of (a) protected-boundary proximity — high by definition, independent of amount — and (b) the consequence engine's own magnitude output, reusing getGoalConsequence/getLiquidityBuffer rather than a new metric.

The hypothesis labels (VERIFIED / STALE / CONFLICTING) are kept as inputs, not adopted as the governor's output states — the output is the four envelopes above, because that's what Machine A's guards actually need to read.

Part 8The failure taxonomy, tested for completeness

CategoryCasesRecovery
Epistemic — "we don't know enough"U1, U2, U3, U7obtain / verify information
Capability — "a rail/tool can't do it"U4, U13degrade / fallback / retry
Authority — "not permitted"U5, U6, U16return control to the human

Not a failure at all, correctly outside the taxonomy: U8, U9, U10, U11, U17 — normal-path variants, memory-governance questions, or legitimate triggers.

The taxonomy is incomplete. U15 fits none of the three: data can be perfect, the rail fully up, the action inside mandate — and Vantage still misses H6's "before commitment" promise, because the window, not evidence or permission, is what failed. A fourth category: accountability-window (timing) failure — "we knew, we could, we were allowed, but too late." Recovery is neither obtain-information, degrade, nor escalate — it's honest relabeling: still useful, never counted as a pre-commitment success (Invariant 8).

Part 10Invariants

The ten given, held as written, plus three found necessary during construction (11–13) and one from red-teaming (14).

  1. No authoritative financial consequence from known-invalid inputs.
  2. The LLM never becomes the source of financial arithmetic.
  3. No financial execution beyond the current authority ceiling.
  4. User silence is never approval for a money-moving action.
  5. Proceeding against Vantage's information never auto-modifies a standing preference.
  6. Missing data never silently becomes zero.
  7. Duplicate events never create duplicate financial effects.
  8. A post-commitment consequence is never logged as a successful pre-decision intervention.
  9. High confidence never overrides an authority boundary.
  10. An explicit instruction overrides an inferred preference.
  11. A CLOSED record is immutable; corrections append, never edit history.
  12. A field classified absent or unresolved-disagree is never treated as adequate merely because retries were attempted.
  13. Every autonomous SILENT/INFORM decision persists the evidence snapshot that justified it — otherwise H4/H5 is unverifiable.
  14. The reasoning step is hard-gated to never exceed the governor's precomputed ceiling — found in the financial-risk red-team, Part 14.

Part 14Red-team

Engineer — "Precedence is under-specified when multiple conditions fire at once." Fixed: an ordered, short-circuiting cascade, not a weighted blend (now explicit in Part 7).
Product manager — "Isn't this three if-statements with ceremony?" The common case genuinely does collapse to a fast early-exit through FULL_ENVELOPE. The machinery is spent only on the ~5–10% of events where a flat rule would silently produce a wrong or defaulted answer. Not modified.
Financial-risk reviewer — "Can the LLM grant itself authority it doesn't have?" The sharpest hit: nothing stopped the reasoning step from exceeding the governor's own ceiling. Fixed, now Invariant 14: the governor runs as deterministic code before reasoning is invoked; the LLM selects only among permitted options, never requests more.
User — "Will this constantly interrupt me?" Fair, and not fully answerable by a state machine — thresholds need real usage data. Structurally biased toward silence in the low-stakes/low-confidence case (U7), which is the common real case. Not modified — a Build-round calibration problem, not a design flaw.
Competition judge — "Agent, or budgeting workflow with agent vocabulary?" Honest answer: the governor is deterministic by design (H1 requires this). Genuine reasoning is confined to RELEVANCE_ASSESSED, only once the governor has already granted an envelope — weighing goals, applying a stated preference to a novel case — never over whether the boundary itself should move. That narrow scoping is the honest answer, not a dodge.

Part 15Originality test

Honest answer: the basic skeleton — observe, assemble, compute, decide, act/inform/ask — is not itself unusual. Three competent teams likely converge on that shape. What would not survive independent reproduction, and is what the final answer leans on:

  1. The governor as a ceiling, not an instruction — four explicit envelopes, permission checked first and independently of evidence.
  2. Silent-logged vs. visible abstention, gated specifically by downside.
  3. The discovered fourth failure category — found only by stress-testing the given taxonomy rather than accepting it as complete.
  4. The hard gate: reasoning can only select among governor-permitted options, never exceed the ceiling.
  5. SILENT's own audit trail, making "fewer unnecessary interventions" falsifiable rather than a slogan.

Part 16Final competition response

Vantage moves through one lifecycle per financial event it observes: assemble the relevant context, compute the deterministic consequence to the user's own stated goals, then decide how much attention the moment deserves. That decision has four honest endings, and only one of them looks like a notification.

If a transaction doesn't materially change the user's goal trajectory, Vantage closes the event silently — logged and auditable, treated as a successful outcome, not a missed chance to speak. If it's meaningful but not urgent, Vantage informs: a plain statement of what changed, a date shift rather than a verdict, with nothing to approve. If it touches a boundary the user set themselves — a minimum emergency buffer, a committed obligation — Vantage's autonomy contracts by rule, not by how confident it feels, and control returns to the person: continue or reconsider, with the consequence shown plainly first. A person who sees an accurate consequence and proceeds anyway is a success, not a failure — Vantage is accountable for the understanding, never for the choice.

Before any of that, Vantage checks what it actually knows. If a fact it needs is missing, stale, or its sources disagree, its usable autonomy shrinks automatically — permission is a ceiling on what Vantage is allowed to do, never an instruction to act regardless of evidence. For something small, this usually means Vantage quietly notes its own uncertainty and says nothing, rather than pestering the user over a trivial amount. For something consequential, it can instead say so out loud: that it doesn't have enough trustworthy information to tell the user what this decision does to their goal, rather than offering a number it can't stand behind. That is correct safety behavior, not a malfunction.

Nothing in this design moves money, cancels a payment, or changes a goal on its own. Even where a supported payment flow could technically hold a transaction pending confirmation, that step always requires the person's explicit go-ahead in the moment — high confidence in the data never substitutes for that authority. When evidence, permission, or timing are ambiguous, the system's default is to say less, not more, and to hand control back to the person rather than guess on their behalf.

Three design insights the state machine exposed

  1. Silence needed its own audit trail to be a real claim, not a slogan — H4/H5 are only falsifiable once every SILENT close carries the evidence that justified it.
  2. Permission and evidence are genuinely separate axes, not one confidence score — the same permitted action can be unusable because the data behind it is weak.
  3. The given failure taxonomy was incomplete — the gap found (timing/accountability-window failure) is the one case where Vantage can be right about everything and still fail H6, purely because it arrived too late.

Three claims to avoid making

01 — Do not claim Vantage can autonomously hold, cancel, or capture a payment through any rail. Always human-gated, in every version of this design.
02 — Do not claim the standing-mandate/intervention-preference mechanism is live. It is specified here, not built.
03 — Do not claim or imply a numeric AI confidence score exists anywhere in this system. There isn't one, deliberately.

Capability gap discovered while constructing the states

The governor's precedence logic — mandate check strictly first and independent of evidence, and the LLM hard-gated to never exceed what the governor permits — has no analogue anywhere in the current codebase. evaluateTransaction in alerts.ts is flat threshold logic with no such gate, no idempotency check, no freshness tracking, and no correction protocol. A new build item, not a refinement of something partially built.
